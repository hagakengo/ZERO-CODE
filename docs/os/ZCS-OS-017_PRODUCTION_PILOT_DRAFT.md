# ZCS-OS-017｜Studio Memory制作連携パイロット設計

状態：DRAFT。隔離Readerと私有コピーを用いる制作前参照・監督資料の試験。本番OS・正式記憶・MASTER・既存PRへの反映はない。

## 制作上の導線

```text
実記憶ノートの読取専用コピー（3件、SHA一致）
  → 隔離Reader（127.0.0.1、認証済み検索・詳細、監査）
  → Work 02独立チャットの制作開始ブリーフ（私有ファイル）
  → Work 01が実候補の既存レビューpacketと照合
  → 監督用ブリーフ（私有ファイル、内容評価のみ）
  → 新しい制作判断があった場合だけ別経路でDRAFT提出
```

既存Reader・Work別短命認証・ZCS-OS-016のパケットを流用する。新しいDB、承認ワークフロー、Reader書込APIはない。ブリーフは正式台帳の代替ではない。

`backend/tools/memory_brief.py`はWork 02の専用資格情報ファイルからtokenを読み、同じ検索語で正式判断限定と全状態を検索し、詳細を取得する。検索と詳細のID・承認状態・範囲・出典の一致を検査する。Readerの障害、approved-only資格情報、結果不一致はエラーとし、「記憶なし」に変換しない。MarkdownとJSONを私有領域に0600で保存し、本文や資格情報はCLIの標準出力に出さない。

`backend/tools/memory_review_brief.py`はWork 02のブリーフと既存DRAFTレビューpacketのSHAを照合し、監督用にQC、過去判断、承認範囲を並べる。技術QC・演出作画QC・監督の内容評価・プロデューサー承認・MASTER・SNS公開を別欄にする。監督の`REVIEW_HOLD`は**提案**であり実候補には記録しない。署名状態も変えない。

## 今回の実制作例

対象はEP00ユナ雨粒5秒、候補`WORK02-EP00-R03-001`。読取専用Readerには関連する別記憶`YUNA-EYE-001`がDRAFTとして存在する。目元について**承認済み記憶は検索結果0件**。既存の`K07-PUBLICATION-001`はX02＋K07のSNS公開範囲だけAPPROVEDで、本編原画・MASTER承認を含まない。ブリーフは「APPROVEDがある」ことと「この制作に適用可能」を自動的に同一視せず、制作への正式適用済み設定を0件とする。

Work 02独立チャットが2026-10-24 JSTに検索2回・詳細1回を実施し、全てHTTP 200。取得IDは`YUNA-EYE-001`、承認状態はDRAFT、出典・承認範囲・関連IDを確認した。Work 02報告のCLI1回・約2.40秒は当該実行の値であり、一般的な所要時間ではない。関連ID`STUDIO-WORKFLOW-001`はメタデータ上で確認したが、詳細取得は未実施。Work 02が保存した制作開始ブリーフは私有領域にある。

Work 01はそのブリーフとZCS-OS-016の既存レビューpacketから監督用ブリーフを生成した。実候補を読み直した結果、出典MATCH、候補DRAFT、実レビュー状態はREVIEW_PENDING。技術QC PASS、演出・作画QC REWORK、内容レビューはREVIEW_HOLD**推奨のみ**、本編MASTER・公開・正式記憶登録は未承認。`YUNA-EYE-001`と候補は関連する別IDで保持する。新しい制作判断は今回生じなかったためDRAFT再提出は行っていない。

私有成果物：`outputs/ZCS_OS017_PILOT_PRIVATE/work02/EP00_YUNA_start_brief.md`、`outputs/ZCS_OS017_PILOT_PRIVATE/work01/EP00_YUNA_director_review_brief.md`、`outputs/ZCS_OS017_PILOT_PRIVATE/ZCS_OS017_independent_connection_evidence.json`。原文や認証情報は公開Gitへ含めない。

## 操作負担と効果の範囲

| 比較 | 今回確認できたこと | 測定していないこと |
| --- | --- | --- |
| Studio Memoryあり | Work 02はCLI1回、Reader検索2回・詳細1回、約2.40秒で出典とDRAFT状態を取得。監督用ブリーフは同じIDと範囲を再利用 | 複数案件での平均、実際の手戻り削減 |
| 従来の手渡し | 原資料の所在、版、承認範囲を都度確認する必要がある | 同条件の所要時間・操作回数は測定なし |

今回の一例から「手戻りが減った」と数値で断定しない。価値として確認できたのは、制作前にDRAFTとSNS公開承認の範囲を表示し、誤認を防げたこと。次回は同一制作課題で手動引継ぎの所要時間と抜け漏れを測り、比較する。

## 正式運用へ進む条件

1. PR #8→#9→#10→#11→#12→#13→#14→本変更を順にレビュー。各段階でデータ形式・認証境界・CIを確認し、マージはプロデューサー判断後に行う。
2. Work 01・02を別macOSユーザー等へ分離し、資格情報ファイルの相互読取拒否を実測する。同一UIDの0700/0600は完全隔離ではない。
3. プロデューサー秘密鍵をWorkから隔離し、人間が署名対象を確認して承認する運用を確立する。実鍵発行は別承認。
4. バックアップのsequence/anchorを同一UIDから独立して保護し、古い・破損snapshotの拒否、復元後のパス再結線、資格情報再発行、旧資格情報失効を試験する。
5. 起動・停止・監査・障害時の責任を明記する。Work 01はReader/提出経路と隔離保存、Work 02は制作出典とDRAFT提出、監督は内容評価、プロデューサーは運用・正式承認を判断する。
6. 受付不一致、出典改変、DRAFTの予期しない昇格、監査失敗、鍵・snapshotの不一致、外部公開疑いでは運用を停止する。

初回の元記憶保管庫はディレクトリ権限が0755だったため、今回のReaderには0700の私有コピーを使った。元領域の権限は変更していない。正式運用前に保管境界を再設計する。
