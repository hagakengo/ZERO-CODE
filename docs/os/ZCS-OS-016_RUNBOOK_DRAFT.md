# ZCS-OS-016｜Studio Memory隔離運用・復旧手順

状態：DRAFT。合成データ用の手順。実制作データ、本番OS、実署名鍵へ適用しない。

## 起動前

1. 対象の私有保管庫、DRAFT候補庫、提出root、Reader認証root、workflow rootを特定する。場所を推測しない。
2. writerを停止し、元ファイルのSHA-256と最新snapshotのsequenceを記録する。snapshot先を私有の別場所に確保する。
3. `python -m tools.memory_backup backup --submission ... --drafts ... --vault ... --workflow ... --reader-auth ... --out ... --anchor ...`でsnapshotを作り、`verify --snapshot ...`で照合する。鍵ファイルは含まない。
4. 提出サービス起動前に`python -m tools.memory_submission recover --root ...`、続いて`check --root ...`を実行する。起動処理も同じ検査を行う。エラーならサービスを起動しない。

## 通常運用

Readerは既存の読み取り専用APIとして起動・停止する。提出サービスは別プロセスで`python -m tools.memory_submission serve --root ... --port ...`を実行し、127.0.0.1だけにバインドする。外部ネットワークへ公開しない。Work 02には`issue --root ... --out ... --ttl ...`で短命の提出専用資格情報を私有ファイルに発行し、Reader用資格情報や人間署名鍵を渡さない。資格情報を失効させるときは`revoke-work02 --root ...`を実行し、古い提出が拒否されることを合成試験で確認する。停止はプロセスを終了し、journal・受付・監査が残るようにする。

提出時は同じ受付IDと同じ内容を使って再送する。受付IDだけを再利用して内容を変えない。`receipts`、`receipt --id ...`、`packet --id ... --out ...`で受付・候補・出典SHA・DRAFT状態を照合する。監督の内容レビュー表示は人間署名付き`DIRECTOR_REVIEWED`ではない。

## 障害後

1. 投稿・登録等の無関係な操作を止め、エラーメッセージと監査イベントの時刻・Work識別子・操作・結果だけを確認する。記憶本文や資格情報をログに写さない。
2. `recover`を実行する。journalにある提出を同じ受付IDで再実行し、不完全な受付を確定扱いしない。
3. `check`で全受付と候補の一致を検証する。不一致・破損・出典の変更があれば停止し、手でAPPROVEDへ直さない。隠しpending/orphanは証拠として保持する。
4. 合成署名付き登録の直後に停止した場合だけ、`python -m tools.memory_workflow --root ... recover-registration --id ...`を使う。署名・diff・隠しstagingが一致しない場合は復旧しない。
5. 検証完了後にサービスを再起動し、DRAFTのまま一覧・詳細・監督パケットを確認する。

## 復元

停止中の隔離環境で`verify --snapshot ...`後、`restore --snapshot ... --out <新しい空パス> --anchor ...`を使う。破損・古いsequence・既存出力先は拒否される。復元先には元の絶対パスを含む設定が残るため、そのままサービスを起動しない。構成と所有者を確認して再結線し、提出・Readerの鍵を新しく発行し、古い資格情報を使えないことを確認する。正式記憶の承認状態と出典SHA、DRAFT候補の状態、失効世代、監査を照合する。秘密署名鍵のバックアップは本手順では実施しない。

## 運用停止条件

受付と候補の不一致、出典SHAの変化、DRAFT以外への予期しない遷移、署名・鍵台帳の不一致、監査保存失敗、資格情報の漏えい疑い、snapshotの破損、Reader/提出サービスの外部公開疑いがあれば停止する。プロデューサー判断前に実データを修復・再承認しない。

## 別macOSユーザーによる隔離計画（未実施）

プロデューサー承認後に専用ユーザーを作り、承認用秘密鍵をWorkと異なる所有者の保護領域に移す。Workユーザーから秘密鍵の読取・署名操作が拒否されること、本人セッションから署名対象を確認できること、失効・更新後に旧鍵署名が拒否されることを試験する。同一ユーザー内の別フォルダーやchmodだけでは隔離済みと判定しない。実鍵発行、OSユーザー作成、権限変更は今回行わない。
